# 14 生产架构与执行计划

## 1. 选择与不选择

推荐采用“一套数据与特征底座、共享内容理解、分场景任务与策略”的模块化系统。第一期保留传统多路召回和分层排序，旁路研究序列大模型；不直接用生成式模型替换整条链路。

技术栈选择必须依现有平台。若从零起步，可用 PyTorch 训练、Kafka 类事件总线、Flink 类流计算、湖仓样本表、KV 在线特征、Faiss 类 ANN 和模型服务；这些是接口角色示例，不是已经安装或推荐必须采购的清单。

## 2. 每个服务的合同

| 组件 | 输入 → 输出 | 一致性与失败策略 |
|---|---|---|
| 请求编排 | user/context → 请求快照与版本包 | 统一 deadline，禁止各下游无限重试 |
| 用户状态 | 截止时间、用户 → 历史与统计 | 记录 feature_time；迟到/重复事件规则固定 |
| 召回路由 | 用户向量/触发内容 → 候选与来源 | 通道超时局部降级，记录来源变化 |
| ANN | 向量、index_version → ID/score | 用户塔、内容塔和索引空间兼容 |
| 候选特征 | IDs、as_of → 批量特征 | 避免逐内容 RPC；缺失有 mask |
| 粗/精排 | 快照特征、model_version → 多任务分数 | shape/schema 校验；错误走稳定旧版 |
| 重排 | 分数、频控状态 → 有序内容 | 强准入、屏蔽永远生效；无解时减少条数 |
| 事件回流 | request/impression/play → 可归因事件 | 幂等键、成熟窗口、删除与保留周期 |

模型包至少含 `feature_schema_version / vocab_version / transform_version / model_version / item_encoder_version / index_version / calibration_version / fusion_version`。允许兼容关系显式登记，不能只把“latest”推到每个服务。

### 最小事件契约

`request_id, impression_id, user_key, item_id, scene, event_type, event_time, ingest_time, position, actual_visibility, model_bundle, player_state, label_attribution_key`。

按数据最小化保存标识，禁止把真实用户日志提交代码仓。列表页可见曝光与视频流有效起播分别产生训练入口，场景间不混淆分母。

## 3. 容量模型：先计算，再选网络

假设性压测场景：峰值 1,000 请求/秒，每请求召回 3,000、粗排保留 300、重排输出 20。精排负载是每秒 30 万候选，而不是 1,000 个单内容预测；50 条历史与 1,000 条历史不能使用同一个服务预算。

若单卡在目标 P99、真实特征和真实候选数下承载 80 请求/秒，按 65% 利用率预算：`ceil(1000/(80×0.65))=20` 卡，再考虑故障域冗余。80 请求/秒为待测参数，不是性能承诺；应避免再把候选吞吐和请求吞吐混算。

1,000 万内容 × 128 维 × FP16 约 2.56 GB 原始向量。实际索引还包含结构、ID 映射、元数据、冗余与增量区；新旧双索引切换会进一步增加内存。Embedding 优化器状态、训练通信与样本缓存不包含在这个数里。

普通 Self-Attention 的 dense attention 状态随 `B×heads×L²` 增长。只把历史从 200 扩到 2,000，其该部分规模增至 100 倍，不是 10 倍；使用高效 kernel 可降低物化开销，但不会让全部投影、参数与通信成本消失。

## 4. 延迟、新鲜度与质量的联合预算

可先设假想端到端服务 P99 为 150 ms，由业务另行确认。分别测用户状态、并行召回、特征获取、精排、重排和网络；各阶段 P99 不能简单相加当作端到端 P99，应使用分布式 trace 重建关键路径。

视频流预取命中率会影响用户可感知延迟；更长缓存也会降低新反馈的利用。需要同时报告播放等待、服务延迟、缓存年龄、状态新鲜度与推荐收益，不能用“后台提前算完”掩盖反馈滞后。

压测包含短/长历史、新/老用户、冷/热缓存、不同候选数与突发流量。吞吐达到目标而 P99 排队失控也判失败。普通 HTTP 开发服务器不承担该压测或生产角色。

## 5. 模型与索引发布流程

1. 冻结数据、特征契约、训练配置和随机种子，输出离线报告。
2. 导出模型并在相同输入上比较训练与服务输出；记录数值容差及排序变化。
3. 若内容塔更新，先构建新索引并回放验证；通过版本包原子切换匹配的用户塔与索引。
4. shadow 流量只测预测与性能，不产生实际用户收益证据；影子流量资源隔离。
5. 小流量验证错误率、准入与降级；再进行预注册、固定随机化单位的 A/B。
6. 分阶段扩大流量，持有已知稳定的模型、索引和融合配置；执行真实回滚演练。

不能只回滚模型而保留不兼容的新索引。在线学习若已修改共享参数，需要快照或隔离写入，否则流量切回不等于状态恢复。

## 6. 12–16 周执行草案

前提：已有合法可用日志、至少一个可部署基线、相应 CPU/GPU 和基础数据平台。若从当前教学仓库从零开始，平台建设与数据采集另行排期，不承诺 16 周生产完成。

| 阶段 | 并行工作包与角色 | 必须交付 | 不满足时 |
|---|---|---|---|
| W1–2 | 算法负责人 + 数据工程 + 产品分析：日志与目标审计 | 指标树、数据字典、缺口和资源表 | 停止效果承诺，先补埋点 |
| W3–5 | 数据工程样本流水线；算法建立召回/精排基线 | 时间切分、特征合同、可复现报告 | 不进入复杂模型研究 |
| W6–8 | 服务工程版本化/ANN；算法做历史与蒸馏对照 | 导出等价、索引切换、容量报告 | 减候选/简化模型或扩资源 |
| W9–12 | 实验分析功效设计；算法灰度；服务演练 | A/A、shadow、受控 A/B、回滚记录 | 修实验或服务，不宣称收益 |
| W13–16 | 通过前期门槛后扩长序列/语义，保留长期对照 | 增量效果与经济验收 | 终止无收益方向，保留旧版 |

角色不是单人全部兼任的假设：至少需要明确算法/训练、数据/实时、服务/平台、实验/产品的责任人。实际人月由已有平台复用程度决定；未确认人力前不写固定人头 ROI。

## 7. 研究与工程交付目录

下一阶段应新增但目前尚不存在：`pipelines/` 时间一致数据流水线、`training/` 数据加载和 checkpoint、`configs/` 冻结实验、`evaluation/` 分层指标、`serving/` 导出与压测、`experiments/` 实验预注册及结果。

每个工作包创建可验收任务，不以“研究某某大模型”作为完成标准。举例：HSTU 对照任务需要训练日志、可复现 config、同预算基线、显存/吞吐、离线结果与明确 go/no-go 结论。
